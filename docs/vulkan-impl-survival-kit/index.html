Vulkan Implementation Survival Kit

How to learn Vulkan and land a working eng::rhi::Device backend in this engine — what to read, in what order, what to let a library do for you, and the specific places this codebase will fight you.

§1The thesis

There are two ways to get Vulkan into this project, and only one of them is worth doing.

The trap is flipping OGRE from RenderSystem_GL3Plus to RenderSystem_Vulkan. It looks like a build-flag change. It is not: OGRE's Vulkan render system accepts only SPIR-V, has no hardware-stencil capability, and cannot host this engine's ImGui path. You would rewrite all 41 shaders to OGRE's SPIR-V conventions, lose the debug UI and the shadows, and still own no Vulkan code at the end. Then you would rewrite the shaders a second time when OGRE leaves.

The path is the one docs/design/2026-07-29-rhi-and-module-contracts.md already committed to: implement eng::rhi::Device in engine/src/rhi/vulkan/ against the contract that exists today, prove it with a triangle and the contract test, and let the renderer migrate onto it milestone by milestone while OGRE keeps drawing the game. Nothing above the RHI knows which backend is live, so nothing above it breaks while you learn.

Why the trap is a trap — measured, not guessed
What breaksEvidence
All shaders. OGRE's Vulkan RS reports language "spirv" only; GLSL must go through Plugin_GLSLang at #version 460 under EShMsgSpvRules, which forbids default-block uniforms. OgreVulkanProgram.cpp:115, OgreGLSLang.cpp:424 — against 41 files of #version 330 core with 111 bare uniform declarations and zero explicit bindings
ImGui. RenderCore drives the vendored docking-branch ImGui through imgui_impl_opengl3 inside an OGRE RenderTargetListener. No GL context under Vulkan, and OGRE's own ImGuiOverlay is already disabled for an ABI clash. RenderCore.cpp:254,306,320; cmake/Dependencies.cmake:216-222
Stencil shadows. The Vulkan RS never sets RSC_HWSTENCIL, so setShadowTechnique logs a warning and forces SHADOWTYPE_NONE. OgreVulkanRenderSystem.cpp:562, OgreSceneManager.cpp:2506
Raw GL in the UI layer — the bitmap font reaches through to the texture's GL id. engine/src/ui/BitmapFont.cpp:30-36

None of that work carries forward. Everything in this kit does.

§2What already exists

More than you'd expect. The seam was cut before the backend was written, which means the shape of the job is already fixed and you are filling in a known interface rather than inventing one.

Three details in that contract were written with Vulkan in mind, and they save you real design work:

  • RenderPassDesc is described per frame, never cached — so you can use dynamic rendering and skip VkRenderPass/VkFramebuffer objects entirely.
  • PipelineDesc already carries colourFormats and depthFormat, which is exactly what VkPipelineRenderingCreateInfo needs.
  • pushConstants documents a 128-byte budget and the null backend enforces it (NullDevice.cpp:89), so it maps to real push constants with no emulation.

§3Challenge register

Everything that will actually cost you time, rated by what it does to the schedule. Blocker stops a stage until solved. Hazard produces a wrong image or a heisenbug rather than an error. Chore is bounded, boring, and must not be underestimated.

Blocker

Vulkan's learning cliff is front-loaded

~1,000 lines before a triangle: instance, physical device, queue families, logical device, swapchain, image views, pipeline, command pool, sync objects. None of it is conceptual — it is structure you must have typed once to reason about.

Mitigation: vk-bootstrap + VMA delete ~60% of it. See Building the backend §2.

Blocker

Synchronization is the actual subject

Barriers, layout transitions, queue submits, fences, semaphores. Get it wrong and you get a correct-looking frame on your GPU and a corrupt one on someone else's. This is the part no library removes.

Budget a full day on this alone. Learning path §3.

Blocker

Shaders must become SPIR-V

41 GLSL 330 files, 111 default-block uniform declarations, no explicit bindings, and preprocessor variants driven from .program scripts. ShaderDesc::code takes SPIR-V bytes, so this needs a compile step in the asset pipeline, not a runtime string.

assets/shaders/*, assets/programs/*.program. Hazards §2.

Hazard

The image is frozen

CLAUDE.md: the PSX look is a shipped result and make visual-test proves no change alters it. Vulkan's Y-down clip space and 0..1 depth range mean your first correct-looking frame will still be upside down or depth-inverted relative to the baselines.

docs/baselines/, make visual-test. Hazards §1.

Hazard

Two windowing paths cannot share one window

Platform pins SDL to X11 and hands OGRE an X11 window id. A Vulkan surface wants SDL_WINDOW_VULKAN on its own window. During the transition the two backends need separate windows — which is an argument for a standalone sample app, not a flag on game.

engine/src/platform/Platform.cpp:28-51. Hazards §4.

Hazard

Resource lifetime is now yours

destroyBuffer cannot free anything the GPU may still be reading. Without a deletion queue keyed to frames-in-flight, you get use-after-free that only reproduces under load.

Building the backend §7.

Chore

Descriptor sets have no analogue in your GL mental model

bindTexture(slot, …) and bindUniformBuffer(slot, …) look like GL binding points and are not. You need a per-frame descriptor allocation strategy before the second draw call, not after.

Building the backend §8.

Chore

Format and state mapping tables

Nine Format values, four blend modes, eight compare ops, five vertex formats. Mechanical, tedious, and the source of a whole class of silent wrong-image bugs when one entry is off.

Types.h. Write it as one table with a static_assert on the enum count.

Chore

The build must not be disturbed

OGRE is compiled from source and a clean build costs many minutes. New CPM dependencies trigger a reconfigure, which is fine; rm -rf build is not.

CLAUDE.md, "Never clean-build".

§4Stage plan

Six stages, each ending in something you can run. The order is chosen so that every stage's proof is mechanical — you never have to squint at a frame and wonder.

0

Read, don't type

½ day

Read engine/src/rhi/null/NullDevice.cpp end to end, then Device.h, then RhiContractTests.cpp. You are implementing that exact sequence. Then read baldurk's Vulkan in 30 minutes for the object graph.

ProofYou can name, from memory, which Vulkan object each of the six handle types in Types.h will wrap.

1

A triangle outside the engine

2–4 days

Follow vulkan-tutorial or vkguide in a scratch directory with vk-bootstrap. Do not try to satisfy the RHI yet. The goal is that the object graph stops being abstract.

ProofA window with a spinning textured quad, zero validation-layer messages.

2

Device creation and capabilities

1–2 days

In-repo. createDevice returns a real device; capabilities() is filled honestly; everything else asserts. Wire CPM deps and the CMake target. Handle the no-window case: the contract test passes nativeWindowHandle = 0, so either return null cleanly or use VK_EXT_headless_surface (this machine advertises it).

Proofctest -R rhi_contract prints vulkan: … instead of not available, and maxSimultaneousLights >= 16.

3

Resources and the contract test

3–5 days

Handle tables (steal the generational Table<> from NullDevice), buffers via VMA, textures with staging uploads and layout transitions, samplers, shaders from SPIR-V, pipelines.

Proofrhi_contract_tests completes the full sequence on Vulkan with a clean validation log.

4

A frame that draws

3–5 days

Swapchain, frames in flight, dynamic rendering, the command list, the deletion queue, resize. Add a tiny rhi_triangle sample app under samples/ with its own SDL window — this is the thing you will debug against for months.

Proofrhi_triangle runs for 10,000 frames, survives window resize, exits clean under validation, and captures in RenderDoc.

5

Port one PSX shader

2–4 days

Take psx.vert/psx.frag to Vulkan GLSL — uniform blocks, explicit bindings, specialization constants in place of the preprocessor variants — and add the offline SPIR-V compile step. One shader teaches you what the other 40 will cost.

ProofThe sample draws a PSX-shaded mesh; screenshot compared against the same mesh under the OGRE path.

What comes after

Stage 5 is the end of this kit. From there the design doc's M2–M5 take over: the engine scene layer, materials, render graph, then cutover. The backend is the easy half; OGRE's SceneManager, MaterialManager and CompositorManager are the expensive half. Don't let a working triangle convince you otherwise.

§5House rules that apply to this work

  • Never clean-build. cmake -S . -B build regenerates makefiles without discarding objects. Killing a build mid-link corrupts the tree.
  • Validation layers on in debug, always. A validation error you scrolled past is the bug you will spend Saturday on. Make the backend log them through eng::log and treat any message as a build failure in tests.
  • Verify on screen. The engine has a deterministic capture hook (RAVEN_SCREENSHOT / RAVEN_SCREENSHOT_FRAME). Give the RHI sample the same one on day one — three real bugs in this repo were invisible to the compiler and obvious in a PNG.
  • Nothing above the RHI changes. If a stage requires editing RenderCore, you have left the plan.
  • No Vulkan type in engine/include/. That rule is what makes the whole approach safe; eng_rhi must keep compiling for callers who never link Vulkan.
