Where this engine specifically will bite

Generic Vulkan advice stops being useful the moment it meets a shipped art direction, 41 GLSL 330 shaders and a window that OGRE already owns.

§1Clip space, depth, and the frozen image

CLAUDE.md states the rule plainly: the PSX look is a shipped result, no change may alter the rendered image, and make visual-test is how that is proven. Vulkan's coordinate conventions differ from OpenGL's in two ways that both produce a plausible-looking but wrong frame.

ConventionOpenGL (today)VulkanSymptom if ignored
Clip-space Y+Y up+Y downThe world renders upside down — a bug this repo has already had once
NDC depth range−1 … 10 … 1Half the depth precision, wrong depth test near the camera, and broken depth metadata
Texture originbottom-lefttop-leftFlipped sampling in the post chain, which reads its own render targets

The clean fix for Y is a negative-height viewport — set VkViewport::y = height and height = -height — which flips the framebuffer without touching a single projection matrix or shader. It has been core since Vulkan 1.1 and it is what you want here precisely because the alternative (flipping the projection) would change the winding order and force you to invert CullMode everywhere.

Depth is not so easily hidden. Build projection matrices for the 0..1 range directly. Watch psx.frag in particular: it consumes the camera far-clip distance as depth metadata, which is also why RenderCore deliberately disables OGRE's infinite far plane (engine/src/render/RenderCore.cpp, the setShadowUseInfiniteFarPlane comment). That value has to stay meaningful through the port.

How to prove the image did not move

Do not eyeball it. Render the same scene through both paths and diff: RAVEN_SCREENSHOT=/tmp/gl.png RAVEN_SCREENSHOT_FRAME=120 ./build/game against the equivalent Vulkan capture, then compare against docs/baselines/. A frame that is vertically mirrored looks fine in a dungeon corridor until you notice the floor is the ceiling.

§2The shader port

41 files in assets/shaders/, all #version 330 core, with 111 default-block uniform declarations and zero explicit bindings. SPIR-V permits none of that. This is the single largest mechanical task in the whole migration.

What you haveWhat SPIR-V needs
#version 330 core#version 450 (or 460)
uniform float affineAmount; — 111 of thesePacked into layout(set=0, binding=0) uniform Params { … } blocks, with std140 layout rules you must respect on the C++ side too
uniform sampler2D tex;layout(set=0, binding=N) uniform sampler2D tex; — every sampler needs an explicit binding
Implicit in/out locationslayout(location=N) on every varying, matched across stages
OGRE auto-params (world_view_proj_matrix, far_clip_distance, light arrays)You supply these. They become fields in your own per-frame / per-object UBOs — which is engine work above the RHI, not backend work.
preprocessor_defines variants in *.program (LIT, METAL, NO_TEXTURE, ALPHA_BLEND, ALPHA_SCISSOR, LIGHT_VOLUME, BLEND_ADD)Either N compiled .spv permutations or SPIR-V specialization constants. Prefer specialization constants: one module, variants resolved at pipeline creation, no combinatorial file explosion.
#include-style shared files (psx_lighting.glsl, surface_common.glsl, scroll_common.glsl, prototype_noise.glsl, portal_pattern.glsl)glslangValidator handles includes with -I; keep the files as they are.
noperspective / smooth interpolation qualifiers — load-bearing for the affine-UV PSX warpSupported unchanged. Do not "clean these up".

Two warnings from experience already recorded in CLAUDE.md, both of which change shape under Vulkan and get better: a material that renders blank is usually a GLSL compile error logged at startup, not a GPU fault; and in GLSL 330 const needs a compile-time-constant initialiser. Offline SPIR-V compilation turns both of those from runtime mysteries into build failures. That is a real argument for doing the compile step early.

§3The PSX chain is the actual product

assets/compositors/psx.compositor is not decoration — it is the game's identity, and reproducing it is the hardest correctness target in the project.

  • The world renders at a third of the window. The pixelation is a genuinely low-resolution framebuffer, not a shader effect. Tiny draw calls in the mrt pass are correct. Your render targets must be sized from that internal resolution, not the swapchain.
  • MRT. The main pass writes multiple attachments. RenderPassDesc::colour is already a vector and DeviceCapabilities::maxColourAttachments already exists — report it honestly from VkPhysicalDeviceLimits::maxColorAttachments.
  • The post passes — bloom_bright, bloom_blur, bloom_composite, dither, pixel_stylize, hardware_resolve — each read the previous pass's output. Every one of those reads is a layout transition and a barrier you owe. This is where synchronization stops being theory.
  • HDR intermediates. Format::RGBA16Float exists in the contract for the bloom targets. Check VK_FORMAT_R16G16B16A16_SFLOAT supports both COLOR_ATTACHMENT and SAMPLED usage on the device before assuming it.
  • Nearest everywhere. FilterMode::Nearest is the default in SamplerDesc and the header says why: "Nearest is not a fallback here: the PSX look depends on unfiltered texels."

§4Windowing, and living beside OGRE

engine/src/platform/Platform.cpp pins SDL_VIDEODRIVER=x11 and hands OGRE an X11 window id, because OGRE's GL3Plus window rejects a Wayland surface. A Vulkan surface wants a window created with SDL_WINDOW_VULKAN. One window cannot be both.

So do not try to add a --render-backend=vulkan flag to game during the transition. Build rhi_triangle as its own binary with its own window, and let the two paths coexist as separate executables until the engine layer above the RHI is ready to switch wholesale. That is also what the design doc's staging assumes.

Silver lining: the X11 pin exists only because of OGRE's GL window. Vulkan speaks Wayland natively through SDL_Vulkan_CreateSurface, so the new path can drop the XWayland workaround — and with it the frame-pacing caveat noted in assets/config/game.toml.

§5Shadows: do not port what is there

The current renderer uses SHADOWTYPE_STENCIL_MODULATIVE — hard-edged stencil shadow volumes, chosen because they are period-correct and need no extra shader plumbing. The design doc already measured them at ~2ms of a 10ms fullscreen frame, scaling with mesh complexity, and concluded the replacement should be shadow maps.

Treat that as settled. Reimplementing stencil volumes on top of a hand-written Vulkan backend would be days of work to reproduce a technique you have already decided to retire — and it is the one part of the frame where "matches the old image exactly" is explicitly not the goal.

§6The bugs you will actually hit

In roughly the order they show up. All five are validation-layer-detectable, which is the argument for keeping the layers on.

Hazard

Black frame, no errors

Usually the swapchain image never left UNDEFINED, or you cleared and then rendered into a different attachment. Check the layout transitions in beginPass before suspecting the shader.

A black screenshot in this repo is also often just an unfocused or offscreen window — confirm against a known-good binary before chasing it.

Hazard

Correct for two frames, then garbage

Classic frames-in-flight bug: a per-frame resource is being written by the CPU while the GPU still reads frame N−2. The inFlight fence wait is either missing or in the wrong place.

Hazard

Texture is transparent, or shows the previous frame

A staging upload without the barrier between vkCmdCopyBufferToImage and the shader read. The Khronos synchronization-examples wiki has this exact case written out — copy it rather than reasoning it through.

Blocker

Crash on window resize

VK_ERROR_OUT_OF_DATE_KHR handled in vkQueuePresentKHR but not in vkAcquireNextImageKHR, or a swapchain destroyed while its images are still in flight. The contract's beginFrame returning false is exactly this path — and rhi_contract_tests calls resizeSwapchain mid-sequence on purpose.

Blocker

Works here, fails on other hardware

Nearly always a missing barrier that your GPU's scheduling happens to hide, or an assumed format/limit. Turn on synchronization validation, and check formats against vkGetPhysicalDeviceFormatProperties rather than hoping.

§7Build and capture hygiene

  • RenderDoc already works. make renderdoc APP=… takes any eng::Application, and RenderDoc's Vulkan support is first-class — better than its GL support, in fact. Read docs/debugging-renderdoc.md before opening a capture; it maps the compositor's render targets and names the failures that look like GPU problems and are not.
  • Debug labels are not optional. Implement pushDebugGroup on day one. A capture of an unlabelled frame is a wall of vkCmdDraw.
  • Object names too. debugName is on every descriptor in Types.h. Feed them to vkSetDebugUtilsObjectNameEXT and every validation message and RenderDoc row becomes readable.
  • Never clean-build. OGRE is compiled from source; a killed link corrupts the tree. cmake -S . -B build regenerates makefiles without discarding objects.
  • Do not touch the GL path to make the Vulkan path easier. Every stage in the plan ends with make run still working. If a change to RenderCore or a shader is required to progress the backend, the plan has been left behind.
